# Forth historical reporting: verified contract and implementation boundary

Reviewed the owner-supplied Swagger 2.0 document (`ResourceServer`, v1) and the accompanying contract notes. The specification declares 29 paths and 40 definitions; all 49 `$ref` uses resolve to a definition. This validates the document structure, not whether the EES Forth account is permitted to call any report.

The documented API host is `webapi.forthtrack.com`, base path `/trackingresource`, over HTTPS. Requests can be JSON, XML or form data; this implementation would send JSON and accept JSON. Every operation declares only a `200` response.

## Supplemental exact shapes from the supplied JSON

- `POST /api/vehicle/accessLocations` and `POST /api/vehicle/accessStartDestinationLocations` both reference `VehicleAccessLocationParams`: required `boxIds`, `startDate`, `endDate`; optional `language`. The first response row `AccessLocation` contains `boxId`, `plateNo`, `vehicleName`, `driver`, `rDate`, `no`, `locationName`, `locationType`, `arriveTime`, `departTime`, `sumDistance`, `parkingEngineOn`, `routingTime`, `stopTime`, `fuelUsaged`, `fuelConsumeRate`, `fuelConsumePerHourRate`. The second `AccessLocationByAddressType` contains `boxId`, `plateNo`, `vehicleName`, `driver`, `rDate`, `source`, `destination`, `departTime`, `arriveTime`, `routingTime`, `runningTime`, `degreeRunningTime`, `parkingTime`, `degreeParkingTime`, `parkingEngineOn`, `degreeParkingEngineOn`, `sumDistance`, `avgSpeed`, `maxSpeed`, `totalMaxSpeed`, `fuelUsaged`, `fuelConsumeRate`, `fuelConsumePerHourRate`, `session`.
- `POST /api/vehicle/speedOverLimits` references `VehicleSpeedOverParams`: required `boxIds`, `startDate`, `endDate`, `seconds`; optional `language`, `ignoreTime` (boolean). `SpeedOverLimit` has `boxId`, `plateNo`, `vehicleName`, `driver`, `rDate`, `startMaxSpeedTime`, `endMaxSpeedTime`, `maxSpeedTime`, `maxSpeed`, `address`, `latitude`, `longitude`.
- `POST /api/vehicle/summaryMonthlys` takes `VehicleStandardParams` and returns `VehicleSummary.SummaryMonthly[]`. Each row has `boxId`, `plateNo`, `vehicleName`, `driver`, `month`, `sumDistance`, `startEngine`, `parkingEngineOn`, `maxSpeed`, `fuelUsaged`, `fuelConsumeRate`, `fuelConsumePerHourRate`, `ev`.
- `GET /api/notificationInfo` returns `NotificationInfo` with `records`, `status`, `totalRecord`; each `Notification` has `notification_id`, `notification_nameT`, `notification_nameE`.
- `POST /api/notification` takes a required body named `conf`, model `NotificationCondition`. Its optional fields are `boxId`, `notificationType`, `ackKnowledge`, `startTime`, `endTime`, `number`, `page`; the spec gives `startTime`/`endTime` as `yyyy-MM-dd HH:mm:ss`. `NotificationList` has `records`, `status`, `totalRecord`, `page`, `number`; rows in `NotificationLogs` have `boxId`, `plate_no`, `driver`, `recDateTime`, `notificationType`, `topic`, `topicE`, `detail`, `latitude`, `longitude`, `site_name`, `ackKnowledge`, `ackDateTime`, `addressT`, `addressE`.
- `GET /api/log/{id}/{starttime}/{endtime}` requires those three path parameters, each typed as string, and returns `Log[]`. In addition to the fields listed in the matrix, `Distance` is int32 with an ambiguous description; `Speed` is int32 km/h, coordinates and `Fuel` are doubles. `IDCard` and `IDTransport` are sensitive and must never be surfaced by a future EES adapter.

## Authentication, effects and limits

Swagger has no `securityDefinitions` and no operation-level security. Its Swagger UI configuration names an `Authorization` header, but it does not specify token issuance, prefix, expiry or report permissions. The existing EES server uses a verified-user plus `business:read` check and a server-only Forth bearer token for the live tracking feed. That profile is reused in code, but its compatibility with history reports is deliberately unverified until an approved test.

Every listed operation documents only HTTP 200. No error schema, maximum date range, maximum device batch, rate limit, retention or report pagination is specified (notification search alone has page/number fields). Source timestamp formats and timezone are not specified. Duration formats/units such as `routingTime`, `duration`, `parkingTime`, `parkingEngineOn` and `stopTime` are not specified. A POST report name and schema do not prove runtime read-only behavior; no history request has been made.

Mutation and command paths are excluded and are never called: `POST /api/asset`, `PUT /api/asset/{assetId}`, `DELETE /api/asset/{assetId}`, `POST /api/assetLog`, `POST /api/assetTrackingLog`, `PUT /api/relay/{boxId}/on`, `PUT /api/relay/{boxId}/off`, `POST /api/trip/start`, and `PUT /api/trip/complete`. Other unreviewed paths (including asset, RFID, current-trip and vehicle-report endpoints) are also not called. The implementation exposes only the `trips` report path through a fixed server-side URL; callers cannot choose an upstream URL or another report endpoint. The request is limited to one device and one calendar day. That route is currently disabled in source pending explicit approval, and no background request or storage exists.

## First bounded test proposed for owner approval

After the owner confirms the report endpoint is authorized and read-only, enable one manual test for one uniquely returned Forth device from the already-authorized fleet and one user-selected calendar day. The server will first use the existing authenticated tracking service to confirm that the device ID appears exactly once in the authorized feed, then make one `trips` report request for that same device and date. It will not persist data or fetch another date/device. Review the response’s raw source/destination/time strings, permission result and error behavior. Do not interpret timezone or `routingTime` until Forth confirms them. No device ID or real date was selected or sent during this implementation.

## Next stages

1. Obtain Forth confirmation of report permissions, auth-header compatibility, report side effects, timezone, timestamp formats, duration units, retention, range/batch limits and rate limits.
2. With approval, run the one-device/one-day `trips` test; keep the returned values raw and review the result before enabling Journey History for office users.
3. Verify `tripDetails` and its location-group source/`duration` semantics before adding location visits.
4. Verify `parkingTrip` and `parkingEngineOverTheLimits` before enabling parking history or engine-idling reporting.
5. Research access-location, speed, monthly-summary and notification behavior separately. Keep route logs out of playback until timestamp, quality, privacy and response-size limits are verified.
