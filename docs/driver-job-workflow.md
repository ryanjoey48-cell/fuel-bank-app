# Driver job workflow

## Deployment

Apply `supabase/migrations/20261003100000_driver_job_events.sql` before testing progress.
It adds `driver_job_events` only; it does not change bookings, assignment, auth, or accounts.
The migration derives the driver/booking foreign-key types from the deployed schema.

The driver cookie is verified by the existing portal session helper. The service-only
`append_driver_job_event` RPC rechecks session expiry/revocation, active linkage,
active driver and booking assignment. It locks the booking before checking event order
and inserting. The unique booking/event constraint also prevents duplicate stages.
No client driver ID, auth ID or timestamp is used. Events are append-only through the API;
the service role has no direct insert/update/delete grants on this table.

## Route source

`lib/ees-depot.ts` contains the verified depot definition extracted unchanged from Shipments.
The driver page reads the existing DEFAULT_DEPOT environment overrides server-side.
Booking Diary currently has a single pickup and a single delivery. Shipment-specific
additional stops are not invented or copied into bookings.

Navigation offers five persistent Google Maps Directions links:
Pickup → Drop-off uses the pickup as origin and delivery as destination; Start from depot
uses depot → pickup → delivery; Start from current location uses current → pickup → delivery;
Directions to pickup and Directions to drop-off use the current origin and a single destination.
Current origin is omitted so Maps resolves the device location; no GPS is invented.
Resolved booking coordinates/place IDs are preferred; unresolved bookings use stored
addresses/names. No Maps API key is needed for these links.

## GPS and events

Optional GPS is requested only on a progress button click. Denial, missing geolocation,
exceptions or timeout use null coordinates and do not block the event. Timestamps are
generated by the database and displayed in Asia/Bangkok. Completion requires confirmation.
No automatic background GPS, POD, photos or signatures are implemented.

## Office retrieval

`GET /api/office/bookings/[bookingId]/driver-events` requires a verified active office
account with existing `business:read` permission; driver linkage still wins and denies
office access. Use a Bearer token like the existing office APIs. The projection includes
event type, timestamp and optional GPS, not driver Auth identity. An office-only RLS
SELECT policy is also available. Booking Diary UI is unchanged; a later read-only detail
panel can consume this API.

## Pilot verification

Sign in normally as the approved Joey Test account. Use only the designated test booking:
check pickup arrival, departure, delivery arrival and completion, refreshing between each.
Verify duplicate/skipped stages return 409, foreign bookings return 404, missing sessions
return 401 and cross-origin writes return 403. Verify office routes remain blocked.
These actions record real test-job events; do not run them against unrelated bookings.

The optional `scripts/verify-driver-job-events.cjs` runs the migration and security/sequence
checks in an isolated PGlite PostgreSQL instance. Install PGlite separately and set
`PGLITE_MODULE_PATH` to its package path; it never reads Supabase credentials or data.
