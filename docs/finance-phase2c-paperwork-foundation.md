# Phase 2C Paperwork Intake foundation

This is an extension of the existing EES Booking Diary and Phase 1B Job Verification. The new `/paperwork-inbox` route uses the existing booking UUID; it does not create a booking or change its operational status. The existing `/finance-demo` remains fixture-only and independent of Supabase.

## Prepared development migration

`20261031100000_finance_paperwork_intake.sql` follows `20261030100000_finance_verification_foundation.sql`. It has **not** been applied to any remote or local Supabase project. It prepares a private `ees-finance-paperwork` bucket with a 10 MB cap and PDF, JPEG, PNG and WebP MIME allowlist. Object keys are generated by a database reservation as `booking UUID/document UUID`, never from the original filename. Upload uses the signed-in user's Storage client with `upsert: false`. Storage INSERT and SELECT policies link the object key to a metadata row, booking UUID and current office account. No Storage UPDATE, DELETE or public URL policy is added.

The document ledger allows multiple attachments per booking, stores original names, type, size, status, uploader, physical-original filing location, reviewer and a revision pointer. A separate append-only event table records reservation, upload, review, rejection and supersession. Client roles receive SELECT through RLS, not direct metadata writes. SECURITY DEFINER functions require active office access and operate on the existing booking ID. Restrictive Storage guards prevent any older permissive policy from opening this bucket or permitting object update/delete. Read-only and driver accounts are denied writes; ordinary admin does not gain finance approval rights. Finance staff with an active office account can view permitted supporting documents, while any future separate finance capability must be reconciled with live account rules.

## Verification gate

Reservation and upload do not mark a job verified. Staff explicitly review the file and record the physical-original location. The subsequent verification function requires a currently reviewed document UUID for each receipt marked received. Missing required documents, open management discrepancies and changed bookings retain the Phase 1B block. Reviewing a revision supersedes its predecessor and invalidates an existing verified handover, requiring office re-verification. Historical source workbook values and the INTEGRA example remain outside this live evidence path.

## Retry and integrity limits

An interrupted upload leaves a pending reservation; the same file can be retried without overwriting an object. Finalization is idempotent and checks Storage's reported MIME and size. Browser code also checks PDF/image signatures, type and size before reserving. **These checks do not prove byte-level integrity against a malicious authenticated client.** Before any production use, add an authorized server-side byte inspection and hash/virus scanning step, verify the actual Supabase Storage metadata contract, and set retention/orphan-cleanup rules without deleting evidence silently. A source booking deleted under existing Diary behavior leaves its finance evidence inaccessible to ordinary users but retained for controlled audit review.
