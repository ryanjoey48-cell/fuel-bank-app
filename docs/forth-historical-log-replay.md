# Historical GPS log replay — offline preparation

The owner reports that Forth's Web API Developer's Guide documents `GET /trackingresource/api/log/{id}/{starttime}/{endtime}` for one device and at most one day, with `yyyyMMddHHmmss` path times and a `Distance` value in metres between successive coordinates. The supplied Forth OpenAPI (`Log_GetLog`) independently confirms the GET path, required string parameters, one-day report description and `Log[]` response. The guide itself was not supplied here; the OpenAPI description of `Distance` is ambiguous. No live log request has been made, so its runtime values, units and behavior remain unverified.

The OpenAPI `Log` model lists `gpsID`, `plateNumber`, `dateTime`, `GPS`, `GPRS`, `Engine`, `Speed` (km/h), `Distance`, sensors, `Latitude`, `Longitude`, `Fuel`, `IDCard`, `IDTransport`, `statusCardReader` and `positionSource` (Unknown/GPS/Wifi/LBS). Fields are not declared required. The offline adapter keeps the original timestamp, source label and coordinates, and excludes identity-card, transport-tag, fuel and sensor values. It retains numeric `Distance` only as a raw source field; the prototype does not show or sum it. The console parking CSV and Swagger vehicle-report APIs remain separate contracts.

The existing EES service authenticates server-side with Forth's OAuth password token profile, a Forth-issued client ID/secret and account credentials, then uses a bearer token for current tracking. That is compatible with the guide's described authentication pattern, but **log endpoint entitlement and bearer acceptance for this EES account are unverified**. The source does not disable TLS validation, and this work adds no history network service or browser credential. A GET path indicates retrieval intent, but the account agreement or Forth must confirm read-only semantics, permitted historical access, audit effects and any limits. Retention, rate limit, response size, pagination, source timezone and timestamp format for real log rows remain unknown.

`lib/forth-history-log.ts` validates one device and a same-calendar-day window no longer than 24 hours. It reuses the current live-field normalizer for coordinate validity, GPS signal, source quality, speed, engine and timezone-aware timestamp parsing; it does **not** reuse live freshness as a historical trust test. A point is replay-verified only when coordinates are valid, GPS signal and source both indicate GPS, and the timestamp resolves unambiguously. Otherwise the raw reading remains visible but is not connected. Straight segments join only consecutive verified samples in source order with increasing timestamps, at most five minutes apart, and without an implausible straight-line speed above 150 km/h. These are conservative prototype display limits, not Forth trip or distance calculations. No road matching, arrival time or travelled distance is inferred.

The development-only `/fleet-route-replay-fixture` page uses synthetic data and the existing Leaflet/OSM map. It is outside the authenticated dashboard so a developer can inspect the fixture without local EES credentials; it contains no live or private data. It is unavailable when `NODE_ENV` is not `development` and has no live API call or data fallback. It shows verified and unverified readings separately, original source timestamps, speed and engine status, and first/last verified points. Production Fleet Tracking and the disabled Journey History gate are untouched.
